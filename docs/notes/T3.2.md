# T3.2 Push Stream, Notification Outbox, and Notification Endpoints

## 1. Overview & Objectives
Task T3.2 ensures customers see real-time status updates (`approval.decided`, `refund.updated`, `proposal.expired`, `notification.new`) immediately over Server-Sent Events (SSE) or polling fallback, while outbound email notifications run reliably through a transactional outbox worker outside any database transaction (`KP-01`). Mail failures retry cleanly with backoff and never roll back returns, refunds, or approvals (`T15`).

## 2. Architecture & Implementation
1. **Push SSE Stream & Polling (`sellershield_agent/events/router.py`, `events/emit.py`, `db.py`)**:
   - `GET /v1/chat/stream` (`Role.customer` required, verified `principal.customer_id`):
     - Parses cursor precedence `Last-Event-ID` > `?since=` > `0`, rejecting non-ASCII, negative, empty, or `> 2^63 - 1` cursors with `422 validation_error` *before* acquiring a stream slot.
     - Enforces max `2` concurrent open streams per `customer_id` using a `threading.Lock`-guarded counter (`429 rate_limited` on the 3rd+ stream); disconnect/cancellation releases slots idempotently via `finally` and `weakref.finalize`.
     - Emits typed SSE frames (`id: <cursor>`, `event: <type>`, `data: <json>` including globally unique `event_id` `CEV-...` for client dedupe), `: heartbeat\n\n` every `20 s`, `15 min` idle cap, `Cache-Control: no-cache`, and `X-Accel-Buffering: no` (`KP-17`).
     - Post-commit cross-thread notification: `write_tx` (`db.py`) triggers `conn.info["_after_commit"]` callbacks after `conn.commit()` and `_db_write_lock` release, signaling customer asyncio queues via `loop.call_soon_threadsafe(...)`; a `2.0 s` database check acts as fallback floor.
   - `GET /v1/me/events?since=&limit=` (`1 <= limit <= 100`, customer-scoped) returns identical ordered JSON envelopes (`has_more`, `next_cursor`) for clients falling back from SSE.
   - Strict `extra="forbid"` schemas in `events/emit.py` reject any unapproved or internal/risk fields (`risk_score`, `limit`, `staff`, `owner`, `reason_text`, etc.).
   - Wired `approval.decided` (`approvals/common_db.py`), `refund.updated` (`execution/refund_webhook_db.py`), `proposal.expired` (`proposals/confirm_audit.py` + `approvals/expire.py`), and `notification.new` (`proposals/confirm_store.py`) to `emit_client_event`.
2. **Notification Outbox Worker & Fixed Templates (`outbox/enqueue.py`, `outbox/worker.py`, `outbox/templates.py`, `outbox/templates/*.txt`)**:
   - Background loop in `main.py` lifespan checks `has_due_email_rows` off the event loop before instantiating `StoreClient`, preventing unnecessary startup work.
   - `process_outbox_batch` claims due `channel == "email"` rows (`queued` / `failed` / `retry_scheduled`, `attempts < 3`, `next_attempt_at <= now` applied in SQL before `.limit()`) atomically (`UPDATE ... WHERE status IN (...)` checking `rowcount == 1`), sends strictly *outside* any transaction via `StoreClient.send_mail` using `ServiceContext` (`Role.service`, deterministic `f"mail:{nid}:{attempt}"` idempotency key), backs off `1 s -> 5 s -> 30 s`, and settles to `exhausted` after `3` failed attempts.
   - Strict DB-owner recipient resolution (`_resolve_customer_id_strict`): resolves customer ID strictly from authoritative DB ownership tables (`cases`, `proposals`, `approvals`, `executions`) or store order records (`_raw_data` / `get_order_admin` outside `write_tx`), completely ignoring payload recipient fields (`to`, `to_addr`, `email`, `recipient`).
   - Five fixed English templates (`approval.decided.txt`, `refund.updated.txt`, `case.created.txt`, `case.message.txt`, `delay.notice.txt`) contain zero forbidden words (`limits?|thresholds?|risks?|scores?|staff|owner|auto|caps?`), enforce ID-only regex-sanitized subjects (`_sanitize_subject_id`), and HTML-escape all body values (`html.escape(..., quote=True)`).
   - Both `approval.decided` and `refund.updated` enqueue email outbox rows with deterministic `dedupe_key`s in the same `write_tx` as their business mutations.
3. **Store Mail Protocol & Adapter (`store/client.py`, `store/fixtures.py`, `store/http_client.py`)**:
   - Implemented `send_mail` on `StoreClient` protocol, in-memory `FixtureStoreClient.mailbox` (supporting `FaultPlan` injection), and HTTP `HttpStoreClient` (`Role.service` / service token only).
4. **Seller Notification Endpoints (`outbox/router.py`, `api/seller_stub.py`, `main.py`)**:
   - `GET /v1/seller/notifications` (seller auth, optional `?status=` filter, uniform error envelope, zero secret/recipient PII leaks beyond DB summary).
   - `POST /v1/seller/notifications/{id}/retry` (seller auth, atomic `UPDATE` resetting `failed`/`exhausted` rows only back to `status="queued", attempts=0, next_attempt_at=None, last_error=None` and recording an immutable `AuditEvent` in the same `write_tx`; `409 invalid_state` on `queued`/`sending`/`sent`).
