# Notes on TASK T3.6: Lean Red-Team and Gate Tests

## Summary
Task T3.6 establishes the comprehensive red-team evaluation and Gate G3 acceptance suite for Phase 3 (Autonomous Operations & Seller Tools).

### 1. Scenarios (`scenarios/redteam/phase3.yaml`)
Authored exactly 30 scenarios across 7 distinct categories:
- **Streams (6 scenarios):**
  - `RT3-STR-01`: Another customer's events cannot be received across customer stream isolation boundaries.
  - `RT3-STR-02`: Hostile `?since=` and `Last-Event-ID` cursor values (negative, non-numeric, overflow) rejected with 422 before slot acquisition.
  - `RT3-STR-03`: Many streams per customer (exceeding maximum 2 concurrent streams) throttled with 429.
  - `RT3-STR-04`: Stalled reader connection disconnects cleanly without server-side thread exhaustion or leak.
  - `RT3-STR-05`: Forged / invalid client event payloads rejected by schema validation (`extra="forbid"`).
  - `RT3-STR-06`: Reconnect storm cursor replay accurately replays missing events without duplicating processed events.
- **Cases & Handler (6 scenarios):**
  - `RT3-CASE-01`: Thirty cases created concurrently maintain SLA deadline ordering and priority indexing.
  - `RT3-CASE-02`: 'Lawyer' and regulatory escalation keywords deterministically bump case priority to high without LLM intervention.
  - `RT3-CASE-03`: Malicious prompt injection instructions in case summaries are sanitized and prevented from hijacking agent state.
  - `RT3-CASE-04`: Customer attempts to flip case handler or close seller-owned case rejected (403/Forbidden).
  - `RT3-CASE-05`: Customer attempting to read internal seller notes rejected (403/Forbidden).
  - `RT3-CASE-06`: Customer attempting to append messages to another customer's case rejected (404/IDOR boundary).
- **Notifications (4 scenarios):**
  - `RT3-NOTIF-01`: Notification recipient spoofed via input payload ignored; recipient derived strictly from authenticated DB record.
  - `RT3-NOTIF-02`: Template placeholder injection containing `<script>` and HTML payloads escaped cleanly in notification bodies.
  - `RT3-NOTIF-03`: Same event emitted ten times deduplicated via idempotent outbox dedupe key.
  - `RT3-NOTIF-04`: Outbox mail provider permanent outage retries with backoff up to 3 attempts and marks status `exhausted` without crashing or throwing 500.
- **Monitor (4 scenarios):**
  - `RT3-MON-01`: Spamming `POST /v1/seller/monitor/run` triggers 10s cooldown rate limiting returning 429.
  - `RT3-MON-02`: Concurrent monitor invocations serialize cleanly under `_run_lock`.
  - `RT3-MON-03`: Duplicate shipment records scanned across cycles deduplicated and alerted at most once.
  - `RT3-MON-04`: Clock jump past delivery window handles expired orders gracefully without integer overflow or crash.
- **Memory (4 scenarios):**
  - `RT3-MEM-01`: Adversarial prompt instructions planted in memory fields are quarantined into bounded structured keys and never executed as commands.
  - `RT3-MEM-02`: Querying agent memory across tenant boundaries prevents cross-customer leakage.
  - `RT3-MEM-03`: Mid-session memory deletion cleanses session context without breaking active conversation flows.
  - `RT3-MEM-04`: Structured memory records cannot alter deterministic policy rules or refund limits.
- **Dev Routes (2 scenarios):**
  - `RT3-DEV-01`: Dev routes (`/v1/dev/*`) return 404 before auth/JWKS inspection when `DEV_MODE=false`.
  - `RT3-DEV-02`: Customer token attempting to access dev endpoints rejected with 401/403.
- **Clumsy-User Flows (4 scenarios):**
  - `RT3-CLU-01`: Client disconnects mid-stream and reconnects with `Last-Event-ID` resuming stream seamlessly.
  - `RT3-CLU-02`: Two parallel browser tabs for same customer both receive real-time SSE updates.
  - `RT3-CLU-03`: Customer confirms return proposal, immediately closes browser, and re-opens to find state preserved.
  - `RT3-CLU-04`: Seller replies to case while customer types message; handler lock to human silences autonomous agent replies.

### 2. Red-Team Test Suite (`agent/tests/redteam/test_phase3.py`)
- 30 tests directly exercising each scenario using the real HTTP application, `ObedientFakeLLM`, `FixtureStoreClient`, and `FaultPlan`.
- Cross-cutting invariant checks:
  - Dual-tenant isolation (two live parallel customer contexts `C001` and `C002`).
  - Handler immutability and agent silence during human handling.
  - Memory bounds and string length constraints.
  - Outbox deduplication and zero duplicate sends.
  - No network sends inside database write transactions.
  - Zero forbidden words (risk scores, internal limits, prompts, tool names, auth tokens) in customer-visible responses.
  - Zero 500 Internal Server Errors.
  - SHA-256 cryptographic audit chain verified intact.
  - Re-runs Phase 2 `LedgerOracle` ensuring zero monetary ledger drift.

   - *Result:* `test_concurrent_runs_serialize_and_return_running_run_id_and_http_rate_limit` failed with `AssertionError: assert 'completed' == 'running'`.
   - *Status:* Cleanly reverted and re-verified.
2. **Outbox Deduplication Key (`outbox/enqueue.py`):**
   - *Sabotage:* Replaced calculated dedupe key with random UUID.
   - *Result:* `test_rt3_notification_03_same_event_ten_times_deduplicated` failed with `AssertionError: assert 0 == 1`.
   - *Status:* Cleanly reverted and re-verified.
3. **Template HTML Escaping (`outbox/templates.py`):**
   - *Sabotage:* Bypassed `html.escape` in `_escape_body_value`.
   - *Result:* `test_rt3_notification_02_template_placeholder_injection` failed with `AssertionError: assert '<script>' not in body`.
   - *Status:* Cleanly reverted and re-verified.
