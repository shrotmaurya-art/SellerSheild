# T3.3 Structured Memory

## 1. Overview & Objectives
Task T3.3 implements visible, safe long-term customer memory with **zero free text**, strictly limited to enums, validated identifiers, non-negative integer counts, and ISO-8601 timestamps (all strings <= 64 characters). Memory never enters deterministic policy (`decide()`) or authorization (`tools/`) code; customer-facing status greeting chips always re-fetch live store/case status rather than caching mutable status words.

## 2. Architecture & Implementation
1. **Database Tables & Schemas (`sellershield_agent/domain/state.py`, `sellershield_agent/memory/models.py`)**:
   - `customer_memory`: `(customer_id PK, profile_json, updated_at)`.
   - `memory_events`: `(event_id PK, customer_id indexed, type, ref_id, outcome, occurred_at)`.
   - `CustomerProfile` (`extra="forbid"`): validates `preferred_language` (`en` | `hi` | `hinglish` | `other`), `last_order_discussed` (`order_id`, `timestamp`), `open_item_ids` (at most 20 open `RET-`, `RFD-`, or `CASE-` IDs), `counts` (`returns`, `refunds`, `cases`), and `last_seen_at`, with a hard `<= 64` character limit on every string.
2. **Deterministic Event Writer (`sellershield_agent/memory/writer.py`)**:
   - `record_memory_event_in_tx(tx, ...)` validates every argument against strict allowlists and regex patterns (`_CUSTOMER_ID_RE`, `_REF_ID_RE`, `_ALLOWED_EVENT_TYPES`, `_ALLOWED_OUTCOMES`, ISO-8601 timestamps <= 64 chars), writes a `memory_events` row atomically in the caller's `write_tx`, updates `CustomerProfile`, enforces idempotent counts per `ref_id`, removes terminal items (`completed`, `resolved`, `failed`, `rejected`) from `open_item_ids`, and caps `open_item_ids` at the most recent 20 items.
   - Wired via single-line in-transaction calls in:
     - `execution/finalize_db.py` (`proposal.succeeded`, `proposal.failed`)
     - `execution/refund_webhook_db.py` (`refund.completed`, `proposal.failed`)
     - `approvals/decide_db.py` (`approval.decided`: `approved`, `rejected`)
     - `approvals/withdraw_db.py` (`proposal.failed`)
     - `cases/api.py` (`case.opened`, `case.resolved`)
3. **Snapshot & Greeting Chips (`sellershield_agent/memory/snapshot.py`, `api/chat.py`, `orchestrator/pipeline.py`)**:
   - `snapshot(customer_id, db_or_conn=None)` and `get_memory_snapshot(db_or_conn, customer_id)` validate stored profile JSON through `CustomerProfile` and generate structured greeting chips (`"Check return RET-xxxx"`, `"Check refund RFD-xxxx"`, `"Check case CASE-xxxx"`) with `action="check_status"`.
   - `POST /v1/chat/sessions` prepends dynamic memory greeting chips alongside default quick-action chips (`chips` and `greeting_chips`).
   - Tapping a status chip in `orchestrator/pipeline.py` routes directly to the live read path (`get_return_status`, `get_refund_status`, `get_customer_case_view`), verifying live store/DB truth via `FactSheet` + `Verifier`.
   - `api/chat.py` (`get_pipeline`) honors `app.dependency_overrides[get_store_client]` so live store reads and tests share the same `StoreClient` instance.
4. **Prompt Data Boundary (`sellershield_agent/understand/service.py`)**:
   - Derives `customer_id` strictly from verified `ctx.customer_id` (never trusting `memory_snapshot["customer_id"]`), validates the snapshot against `CustomerProfile` (`extra="forbid"`), and embeds only compact sorted JSON inside `<data><memory>...</memory></data>`.
5. **Memory Erasure (`sellershield_agent/memory/router.py`)**:
   - `DELETE /v1/me/memory` requires `require_customer`, atomically deletes all `customer_memory` and `memory_events` rows for `principal.customer_id`, writes `AuditEvent(action="erase_memory", outcome=Outcome.SUCCESS)`, and returns strict OpenAPI `{"erased": True}`.
