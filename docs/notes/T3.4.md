# T3.4 Proactive Delay Monitor

## 1. Overview & Objectives
Task T3.4 implements the autonomous proactive delay monitor for SellerShield AI.
Without waiting for a customer complaint, the monitor automatically scans store shipments for delays, notifies affected customers once, and opens high-priority support cases for lost shipments or carrier exceptions >= 5 days.

Key requirements:
1. **StoreClient Protocol & Implementations**:
   - `list_shipments_for_monitor(service_ctx, statuses, limit, cursor)` implemented across `StoreClient` protocol, `FixtureStoreClient`, and `HttpStoreClient`.
   - Enforces service-role authentication (`Role.service`) and blocks customer tokens or tainted tokens with `StoreForbidden`.
   - `HttpStoreClient` queries `/admin/shipments` with client credentials service token.
2. **Proactive Monitor Service (`sellershield_agent/monitor/service.py`)**:
   - `run_monitor(service_ctx, clock, store_client=store, engine=engine)`:
   - Evaluates shipment timeliness using simulated `Clock` and Asia/Kolkata timezone policies.
   - For `options` (delay >= 2 days or carrier exception < 5 days):
     - Enqueues `delay.notice` notification to outbox with strict deduplication key `delay:{order_id}:{eta_date}:{kind}`.
     - Emits `monitor.notice` client event with 3 guided action chips: "Wait" (`track_order`), "Cancel if not delivered" (`talk_to_human`), and "Talk to support" (`talk_to_human`).
   - For `lost` or carrier exceptions >= 5 days:
     - Automatically opens high-priority case with deterministic brief (`"reship or refund with approval"` for lost; `"wait or cancel"` for delivery delay).
     - Emits `case_opened` event into `case_events`.
   - Records run statistics in `monitor_runs` (`scanned`, `flagged`, `notified`, `skipped_duplicates`, `cases_created`, `summary_json`).
   - Deduplicates across runs and within pages using `monitor_events` table keys (`{order_id}:{eta_date}:{kind}`). Running twice creates zero new notifications or cases (T18).
   - Concurrency protection: `_run_lock` serializes concurrent runs. A concurrent caller gets the active running `run_id` without duplicating store scans.
   - Cap: at most 200 shipments per run with cursor pagination and loop guard.
3. **Seller Monitor API (`sellershield_agent/monitor/router.py`)**:
   - `POST /v1/seller/monitor/run`: triggers manual run (guarded by `require_seller`, 10 s cooldown per clock returning 429 `rate_limited`).
   - `GET /v1/seller/monitor/runs`: returns list of monitor run summaries.
   - `GET /v1/seller/monitor/runs/{id}`: returns specific monitor run summary.
