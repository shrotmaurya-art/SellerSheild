# T3.1 Cases, Escalation Triggers and Handler Model

## 1. Overview & Objectives
Task T3.1 implements persistent customer support cases, deterministic briefs, escalation triggers, and the atomic handler model (`agent` <-> `human`).
The core invariant is that the seller and the autonomous agent never talk over each other: once a seller replies, the handler atomically flips to `human`, and the agent remains silent (saying only "A team member is handling this" plus read-only status) and never calls propose tools.

## 2. Architecture & Implementation
1. **Data Model Extensions (`sellershield_agent/domain/state.py`)**:
   - `cases`: Added `session_id` (indexed, nullable), `handler` (`String(32)`, default `"agent"`), `version` (default 1), `priority` (`normal` [24h SLA] or `high` [2h SLA]), and lifecycle statuses (`open`, `in_review`, `waiting_for_customer`, `waiting_for_seller`, `resolved`, `closed`).
   - `case_events`: Stores append-only audit trail of messages, status transitions, assignments, and handbacks.
2. **Escalation Triggers (`sellershield_agent/orchestrator/escalation.py`)**:
   - Evaluated in precedence order:
     1. Legal or threat keywords (`lawyer`, `legal`, `court`, `consumer forum`, `fraud`, `sue`, `police`) from policy -> high-priority case (2h SLA on the `Clock`).
     2. Policy decision `ESCALATE` -> normal-priority case.
     3. Customer asks for a human (`HUMAN_REQUEST`) -> normal-priority case.
     4. Customer angry twice in a row -> offers interactive `"Talk to Human"` chip without creating a case.
   - 30-minute idempotency window: at most one active case per `(customer_id, category, order_id)`.
   - Every evaluated trigger logs an immutable `AuditEvent` (`EventType.POLICY_DECISION`, `action="escalation_trigger"`).
3. **Deterministic Brief Builder (`sellershield_agent/cases/brief.py`)**:
   - `build_deterministic_brief`: Builds structured case summary without LLM model text.
   - Customer request text is sanitized of secret tokens (`Bearer`, `api_key`, `secret_token`) and HTML-escaped with `verified: False`.
   - Next-step recommendations derive strictly from a deterministic category/facts rule table (`lost_shipment` -> `"reship or refund with approval"`, `delivery_delay` -> `"wait or cancel"`, `damaged_item`/`wrong_item` -> `"review"`, `angry` -> `"reply within the SLA"`). Customer text cannot steer recommendations.
   - Seller-only risk signals and policy rules are segregated.
4. **API Endpoints (`sellershield_agent/cases/router.py`)**:
   - Customer:
     - `GET /v1/me/cases`: lists caller's cases (strips internal seller notes and risk signals).
     - `GET /v1/me/cases/{id}`: returns case thread with uniform 404 on unowned cases (IDOR defense).
     - `POST /v1/me/cases/{id}/messages`: appends customer message; cannot flip handler.
   - Seller:
     - `GET /v1/seller/cases`: filterable by `status` and `priority`.
     - `GET /v1/seller/cases/{id}`: full details including brief and events.
     - `GET /v1/seller/cases/{id}/brief`: structured brief facts.
     - `POST /v1/seller/cases/{id}/messages`: atomic compare-and-set flips handler to `human` and increments version; emits `case.message` client event and enqueues outbox notification.
     - `POST /v1/seller/cases/{id}/status`: updates case status; emits `case.status` client event and enqueues notification.
     - `POST /v1/seller/cases/{id}/assign`: assigns case to staff member.
     - `POST /v1/seller/cases/{id}/handback`: restores handler to `agent`.
5. **Handler Synchronization (`sellershield_agent/orchestrator/pipeline.py`)**:
   - Inspects `sessions.c.handler`. If `"human"`, immediately returns `"A team member is handling this case..."` and executes zero propose tools.
