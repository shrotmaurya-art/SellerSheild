# T3.0 Shared Stubs and Setup

## Overview
Shared interfaces and database tables established for Phase 3 parallel development across:
1. `events`: Client event emission with per-type strict Pydantic schemas (`extra='forbid'`) and cursor returns.
2. `outbox`: Notification outbox queueing with deterministic deduplication by `dedupe_key`.
3. `cases`: Customer support case escalation, SLA calculation (2h high, 24h normal), case opening event recording, and minimal brief stub.
4. `routers`: Empty router stubs registered in `main.py` for `events`, `outbox`, `cases`, `memory`, `monitor`, and `dev` so upcoming Phase 3 tasks (`T3.1`, `T3.2`, etc.) develop in isolation without modifying `main.py`.

## Data Model Additions
- `cases`: `case_id`, `customer_id`, `order_id`, `category`, `priority`, `status`, `assignee`, `brief_json`, `sla_due_at`, `resolution_code`, `evidence_ids_json`, `created_at`, `resolved_at`, `version`.
- `case_events`: `event_id`, `case_id`, `actor_type`, `actor_id`, `kind`, `text`, `created_at`.
- `notifications_outbox`: Spec §10 columns (`notification_id`, `channel`, `customer_id`, `template`, `payload_json`, `dedupe_key`, `status`, `attempts`, `next_attempt_at`, `last_error`, `created_at`).
- `client_events`: Spec §10 and §21 amendment 4 columns (`event_id`, `customer_id`, `type`, `payload_json`, `created_at`).

## Invariants & Defenses
- Strict Pydantic V2 validation with `extra='forbid'` prevents unauthorized payload fields, customer PII leaks, or internal risk/score fields from entering customer `client_events`.
- Atomic `dedupe_key` checking and fallback prevents duplicate notification creation across retries.
- SLA due calculations enforce 2-hour high priority and 24-hour normal priority SLAs measured in UTC timestamps.
- All router registrations are decoupled into per-feature modules.
